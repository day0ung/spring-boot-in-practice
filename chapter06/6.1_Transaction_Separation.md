# 6.1 트랜잭션 코드의 분리

## 문제 상황

- `UserService`의 `upgradeLevels()`에는 비즈니스 로직과 트랜잭션 코드가 혼재
- 트랜잭션 코드가 비즈니스 로직을 감싸고 있어 분리가 필요

```java
public void upgradeLevels() {
    // 트랜잭션 코드 (비즈니스 로직과 무관)
    TransactionStatus status =
        transactionManager.getTransaction(new DefaultTransactionDefinition());
    try {
        // 비즈니스 로직
        List<User> users = userDao.getAll();
        for (User user : users) {
            if (canUpgradeLevel(user)) upgradeLevel(user);
        }
        transactionManager.commit(status);
    } catch (RuntimeException e) {
        transactionManager.rollback(status);
        throw e;
    }
}
```

## 비즈니스 로직 분리

- 비즈니스 로직만 담는 메서드를 별도로 추출

```java
public void upgradeLevels() {
    TransactionStatus status =
        transactionManager.getTransaction(new DefaultTransactionDefinition());
    try {
        upgradeLevelsInternal(); // 비즈니스 로직 위임
        transactionManager.commit(status);
    } catch (RuntimeException e) {
        transactionManager.rollback(status);
        throw e;
    }
}

private void upgradeLevelsInternal() {
    List<User> users = userDao.getAll();
    for (User user : users) {
        if (canUpgradeLevel(user)) upgradeLevel(user);
    }
}
```

## DI를 이용한 클래스 분리

- 트랜잭션 코드와 비즈니스 로직을 **아예 다른 클래스**로 분리
- 클라이언트가 두 클래스를 모두 알지 않도록 **인터페이스** 도입

```java
public interface UserService {
    void add(User user);
    void upgradeLevels();
}
```

```java
// 비즈니스 로직 담당
public class UserServiceImpl implements UserService {
    public void upgradeLevels() {
        List<User> users = userDao.getAll();
        for (User user : users) {
            if (canUpgradeLevel(user)) upgradeLevel(user);
        }
    }
}
```

```java
// 트랜잭션 담당 (데코레이터 패턴)
public class UserServiceTx implements UserService {
    private UserService userService; // 실제 비즈니스 로직 위임 대상
    private PlatformTransactionManager transactionManager;

    public void setUserService(UserService userService) {
        this.userService = userService;
    }

    public void upgradeLevels() {
        TransactionStatus status =
            transactionManager.getTransaction(new DefaultTransactionDefinition());
        try {
            userService.upgradeLevels(); // 비즈니스 로직 위임
            transactionManager.commit(status);
        } catch (RuntimeException e) {
            transactionManager.rollback(status);
            throw e;
        }
    }
}
```

## 빈 설정

```xml
<bean id="userService" class="...UserServiceTx">
    <property name="transactionManager" ref="transactionManager" />
    <property name="userService" ref="userServiceImpl" />
</bean>

<bean id="userServiceImpl" class="...UserServiceImpl">
    <property name="userDao" ref="userDao" />
    <property name="mailSender" ref="mailSender" />
</bean>
```

## 분리의 장점

| 항목 | 분리 전 | 분리 후 |
|---|---|---|
| 비즈니스 로직 테스트 | 트랜잭션 설정 필요 | `UserServiceImpl`만 단독 테스트 가능 |
| 트랜잭션 기술 변경 | `UserService` 수정 | `UserServiceTx`만 수정 |
| 비즈니스 로직 집중도 | 트랜잭션 코드가 섞임 | 순수 비즈니스 로직만 존재 |

## 정리

> 트랜잭션 코드를 `UserServiceTx`로 분리하면 `UserServiceImpl`은 순수한 비즈니스 로직만 담게 되어  
> 테스트가 쉬워지고 각 클래스의 책임이 명확해진다. 이것이 AOP의 출발점이다.
