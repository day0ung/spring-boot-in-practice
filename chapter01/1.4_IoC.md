# 1.4 제어의 역전 (IoC, Inversion of Control)

## 오브젝트 팩토리

- 기존 `UserDaoTest`는 UserDao가 어떤 `ConnectionMaker`를 사용할지 결정하는 책임까지 갖고 있었음
- 이 관심사를 분리하기 위해 **팩토리 클래스(`DaoFactory`)** 를 도입
- `DaoFactory`가 오브젝트 생성 방법을 결정하고 만들어진 오브젝트를 반환

```java
public class DaoFactory {
    public UserDao userDao() {
        return new UserDao(new DConnectionMaker());
    }
}
```

- `UserDaoTest`는 이제 `DaoFactory`에 요청해서 UserDao를 받아 사용하기만 하면 됨

## 오브젝트 팩토리의 활용

- DAO가 여러 개일 경우 `ConnectionMaker` 생성 코드가 중복됨
- 중복 제거를 위해 `ConnectionMaker`를 생성하는 메서드를 별도로 분리

```java
public class DaoFactory {
    public UserDao userDao() {
        return new UserDao(connectionMaker());
    }

    public AccountDao accountDao() {
        return new AccountDao(connectionMaker());
    }

    public ConnectionMaker connectionMaker() {
        return new DConnectionMaker();
    }
}
```

## 제어의 역전

- 일반적인 프로그램: 오브젝트가 자신이 사용할 오브젝트를 **스스로 결정하고 생성**
- 제어의 역전: 오브젝트 자신이 사용할 오브젝트를 **스스로 선택하지 않음**, 생성도 하지 않음
  - 자신이 어떻게 만들어지고 어디서 사용되는지 알 수 없음
  - 모든 제어 권한을 자신이 아닌 **다른 대상에게 위임**

- `UserDao`는 자신이 어떤 `ConnectionMaker`를 사용할지 알지 못함 → `DaoFactory`가 결정
- `UserDaoTest`도 마찬가지로 `DaoFactory`에 제어권을 넘김

## 프레임워크 vs 라이브러리

| | 라이브러리 | 프레임워크 |
|---|---|---|
| 제어 흐름 | 개발자가 직접 제어 | 프레임워크가 제어 |
| IoC 적용 | X | O |

- **프레임워크는 IoC 개념이 적용된 대표적인 사례**
- 개발자가 작성한 코드는 프레임워크에 의해 사용됨 (제어권이 역전)

## 정리

> 제어의 역전이란, 오브젝트가 자신이 사용할 오브젝트를 스스로 선택·생성하지 않고,  
> 외부(팩토리, 컨테이너 등)가 그 제어권을 가져가는 것을 말한다.
