# 3.2 변하는 것과 변하지 않는 것

## JDBC try/catch/finally 코드의 문제점

- DB 연결, 예외 처리, 자원 반납 코드가 모든 메서드에 중복됨
- 실수로 `finally` 블록에서 `close()`를 빠뜨리면 DB 커넥션 누수 발생

```java
public void deleteAll() throws SQLException {
    Connection c = null;
    PreparedStatement ps = null;
    try {
        c = dataSource.getConnection();
        ps = c.prepareStatement("delete from users"); // 변하는 부분
        ps.executeUpdate();
    } catch (SQLException e) {
        throw e;
    } finally {
        if (ps != null) try { ps.close(); } catch (SQLException e) {}
        if (c != null) try { c.close(); } catch (SQLException e) {}
    }
}
```

- **변하지 않는 부분**: try/catch/finally 자원 관리 코드
- **변하는 부분**: 실제 SQL을 실행하는 코드 (`ps = c.prepareStatement(...)`)

## 분리와 재사용을 위한 디자인 패턴 적용

### 메서드 추출

- 변하는 부분을 별도 메서드로 추출

```java
private PreparedStatement makeStatement(Connection c) throws SQLException {
    return c.prepareStatement("delete from users");
}
```

- 변하는 부분을 추출했지만, 재사용이 오히려 어려워짐 → 적합하지 않은 방법

### 템플릿 메서드 패턴 적용

- 변하지 않는 부분을 슈퍼클래스에, 변하는 부분을 서브클래스에 두는 방식

```java
// 슈퍼클래스
public abstract class UserDao {
    public void deleteAll() throws SQLException {
        Connection c = null;
        PreparedStatement ps = null;
        try {
            c = dataSource.getConnection();
            ps = makeStatement(c); // 추상 메서드 호출
            ps.executeUpdate();
        } catch (SQLException e) { throw e; }
        finally { /* close */ }
    }

    protected abstract PreparedStatement makeStatement(Connection c) throws SQLException;
}

// 서브클래스
public class UserDaoDeleteAll extends UserDao {
    protected PreparedStatement makeStatement(Connection c) throws SQLException {
        return c.prepareStatement("delete from users");
    }
}
```

**템플릿 메서드 패턴의 단점**

- DAO 로직마다 새로운 서브클래스를 만들어야 함
- 컴파일 시점에 이미 관계가 결정되어 유연성이 떨어짐

### 전략 패턴 적용

- 변하는 부분(SQL 실행)을 별도의 **전략 인터페이스**로 분리

```java
public interface StatementStrategy {
    PreparedStatement makePreparedStatement(Connection c) throws SQLException;
}
```

```java
// 구체 전략 클래스
public class DeleteAllStatement implements StatementStrategy {
    public PreparedStatement makePreparedStatement(Connection c) throws SQLException {
        return c.prepareStatement("delete from users");
    }
}
```

```java
// 컨텍스트: 변하지 않는 부분
public void jdbcContextWithStatementStrategy(StatementStrategy stmt) throws SQLException {
    Connection c = null;
    PreparedStatement ps = null;
    try {
        c = dataSource.getConnection();
        ps = stmt.makePreparedStatement(c);
        ps.executeUpdate();
    } catch (SQLException e) { throw e; }
    finally {
        if (ps != null) try { ps.close(); } catch (SQLException e) {}
        if (c != null) try { c.close(); } catch (SQLException e) {}
    }
}
```

```java
// 클라이언트: 전략을 선택하고 컨텍스트 호출
public void deleteAll() throws SQLException {
    StatementStrategy st = new DeleteAllStatement();
    jdbcContextWithStatementStrategy(st);
}
```

## 클라이언트/컨텍스트 분리

전략 패턴에서 각 역할의 책임:

| 역할 | 담당 | 책임 |
|---|---|---|
| 클라이언트 | `deleteAll()` 등 개별 메서드 | 전략 오브젝트 생성 및 컨텍스트 호출 |
| 컨텍스트 | `jdbcContextWithStatementStrategy()` | 변하지 않는 작업 흐름 실행 |
| 전략 | `StatementStrategy` 구현체 | 변하는 SQL 로직 |

- 이 구조가 바로 **템플릿/콜백 패턴**의 기반이 됨

## 정리

> 코드에서 변하는 부분과 변하지 않는 부분을 분리하는 것이 핵심이다.  
> 전략 패턴을 적용하면 변하지 않는 컨텍스트(자원 관리)와 변하는 전략(SQL 로직)을  
> 깔끔하게 분리할 수 있다.
