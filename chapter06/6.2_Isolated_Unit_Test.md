# 6.2 고립된 단위 테스트

## 복잡한 의존관계의 문제

- `UserService`는 `UserDao`, `MailSender`, `PlatformTransactionManager`에 의존
- 단위 테스트 시 이 의존 오브젝트들이 모두 필요 → 진정한 단위 테스트가 아님

```
UserServiceTest
    └── UserService
            ├── UserDao ──▶ DB
            ├── MailSender ──▶ 메일 서버
            └── TransactionManager ──▶ DB
```

## 테스트 대역을 이용한 고립

- 의존 오브젝트를 **목 오브젝트(Mock Object)** 로 대체하여 외부 의존 제거

```
UserServiceTest
    └── UserServiceImpl
            ├── MockUserDao (목)
            ├── MockMailSender (목)
            └── (트랜잭션 없음 - UserServiceImpl은 순수 비즈니스 로직)
```

### MockUserDao 구현

```java
public class MockUserDao implements UserDao {
    private List<User> users;
    private List<User> updated = new ArrayList<>();

    public MockUserDao(List<User> users) { this.users = users; }

    public List<User> getUpdated() { return updated; }

    public List<User> getAll() { return this.users; }

    public void update(User user) { updated.add(user); }

    // 사용하지 않는 메서드는 UnsupportedOperationException
    public void add(User user) { throw new UnsupportedOperationException(); }
    public User get(String id) { throw new UnsupportedOperationException(); }
    public void deleteAll() { throw new UnsupportedOperationException(); }
    public int getCount() { throw new UnsupportedOperationException(); }
}
```

### 고립된 테스트 코드

```java
@Test
public void upgradeLevels() throws Exception {
    UserServiceImpl userServiceImpl = new UserServiceImpl();

    MockUserDao mockUserDao = new MockUserDao(this.users);
    userServiceImpl.setUserDao(mockUserDao);

    MockMailSender mockMailSender = new MockMailSender();
    userServiceImpl.setMailSender(mockMailSender);

    userServiceImpl.upgradeLevels();

    // 업그레이드 결과 검증
    List<User> updated = mockUserDao.getUpdated();
    assertThat(updated.size(), is(2));
    checkUserAndLevel(updated.get(0), "joytouch", Level.SILVER);
    checkUserAndLevel(updated.get(1), "madnite1", Level.GOLD);

    // 메일 발송 검증
    List<String> request = mockMailSender.getRequests();
    assertThat(request.size(), is(2));
}
```

## 단위 테스트 vs 통합 테스트

| 구분 | 단위 테스트 | 통합 테스트 |
|---|---|---|
| 범위 | 단일 클래스/메서드 | 여러 계층, 외부 시스템 포함 |
| 속도 | 빠름 | 느림 |
| 목적 | 로직 검증 | 연동 검증 |
| 목 사용 | 적극적으로 사용 | 실제 오브젝트 사용 |
| 실패 원인 파악 | 명확 | 복잡 |

### 테스트 방법 선택 가이드

- 항상 **단위 테스트를 먼저** 고려
- 외부 리소스를 사용해야 할 때 통합 테스트
- DAO는 DB까지 연동하는 통합 테스트가 필요 (SQL, 매핑 검증)
- 여러 단위가 상호작용할 때 통합 테스트로 전체 흐름 검증

## Mockito 프레임워크

- 목 오브젝트를 직접 만드는 대신 Mockito를 사용하면 간단하게 생성 가능

```java
UserDao mockUserDao = mock(UserDao.class);
when(mockUserDao.getAll()).thenReturn(this.users);
doNothing().when(mockUserDao).update(any(User.class));

userServiceImpl.setUserDao(mockUserDao);
userServiceImpl.upgradeLevels();

// 검증
verify(mockUserDao, times(2)).update(any(User.class));
verify(mockUserDao).update(users.get(1));
verify(mockUserDao).update(users.get(3));
```

- `mock()`: 목 오브젝트 생성
- `when().thenReturn()`: 특정 메서드 호출 시 반환값 지정
- `verify()`: 메서드 호출 여부/횟수 검증

## 정리

> 목 오브젝트를 활용한 고립된 단위 테스트는 외부 의존 없이 빠르고 정확하게 비즈니스 로직을 검증한다.  
> Mockito를 사용하면 목 오브젝트 구현 코드를 최소화하고 검증을 선언적으로 표현할 수 있다.
