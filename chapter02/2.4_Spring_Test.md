# 2.4 스프링 테스트 적용

## 테스트를 위한 애플리케이션 컨텍스트 관리

- `@Before`에서 매번 `ApplicationContext`를 새로 생성하면 테스트마다 컨텍스트가 만들어짐
- 컨텍스트 생성 비용이 크므로 **여러 테스트가 컨텍스트를 공유**하는 방식이 효율적

### 스프링 테스트 컨텍스트 프레임워크 적용

```java
@RunWith(SpringJUnit4ClassRunner.class)
@ContextConfiguration(locations = "/applicationContext.xml")
public class UserDaoTest {

    @Autowired
    private ApplicationContext context;

    private UserDao dao;

    @Before
    public void setUp() {
        this.dao = context.getBean("userDao", UserDao.class);
    }
}
```

- `@RunWith(SpringJUnit4ClassRunner.class)`: JUnit이 테스트를 실행할 때 스프링 테스트 컨텍스트 프레임워크를 사용하도록 지정
- `@ContextConfiguration`: 설정 파일의 위치를 지정
- 스프링은 테스트 클래스 전체에서 **하나의 컨텍스트를 공유**함

### 테스트 메서드의 컨텍스트 공유

- 같은 설정 파일을 사용하는 테스트는 컨텍스트를 공유
- JUnit은 테스트마다 새 인스턴스를 만들지만, 스프링 컨텍스트는 한 번만 생성되고 재사용됨

```
테스트1 실행 → ApplicationContext 생성
테스트2 실행 → 동일한 ApplicationContext 재사용
테스트3 실행 → 동일한 ApplicationContext 재사용
```

### 테스트 클래스의 컨텍스트 공유

- `@ContextConfiguration`에 동일한 설정 파일을 지정한 다른 테스트 클래스끼리도 컨텍스트 공유 가능
- 테스트 전체 실행 시간을 크게 줄일 수 있음

## @Autowired

- 스프링 DI에 사용되는 어노테이션으로, **타입을 기준으로 빈을 자동 주입**
- `ApplicationContext` 자체도 빈으로 등록되어 있으므로 `@Autowired`로 주입 가능
- 빈을 직접 주입받을 수도 있어 `getBean()` 없이 더 간결하게 작성 가능

```java
@Autowired
private UserDao dao; // ApplicationContext 없이 직접 주입
```

- 같은 타입의 빈이 여러 개라면 **변수명과 일치하는 빈 이름**으로 선택

## DI와 테스트

### 테스트 코드에 의한 DI

- 테스트에서 특정 빈의 의존 오브젝트를 수동으로 바꿔 사용하고 싶을 때

```java
@DirtiesContext // 컨텍스트 상태를 변경했음을 표시 → 해당 테스트 후 컨텍스트 재생성
@Test
public void andAndGet() throws SQLException {
    DataSource testDataSource = new SingleConnectionDataSource(
        "jdbc:mysql://localhost/testdb", "spring", "book", true);
    dao.setDataSource(testDataSource);
    // ...
}
```

- `@DirtiesContext`: 테스트가 컨텍스트의 상태를 변경했을 때 다음 테스트를 위해 컨텍스트를 새로 만들도록 지시
- 컨텍스트 공유 이점이 사라지므로 사용을 최소화하는 것이 좋음

### 테스트를 위한 별도의 DI 설정

- 운영용 `applicationContext.xml`과 별개로 **테스트 전용 설정 파일**을 만드는 방법

```xml
<!-- test-applicationContext.xml -->
<bean id="dataSource"
      class="org.springframework.jdbc.datasource.SimpleDriverDataSource">
    <property name="driverClass" value="com.mysql.jdbc.Driver" />
    <property name="url" value="jdbc:mysql://localhost/testdb" />
    <property name="username" value="spring" />
    <property name="password" value="book" />
</bean>
```

```java
@ContextConfiguration(locations = "/test-applicationContext.xml")
public class UserDaoTest { ... }
```

- `@DirtiesContext` 없이도 테스트용 DB를 사용할 수 있어 권장하는 방식

### 컨테이너 없는 DI 테스트

- 스프링 컨테이너 없이 순수하게 `UserDao`를 직접 생성하고 의존 오브젝트를 수동 주입

```java
public class UserDaoTest {
    private UserDao dao;

    @Before
    public void setUp() {
        dao = new UserDao();
        DataSource dataSource = new SingleConnectionDataSource(
            "jdbc:mysql://localhost/testdb", "spring", "book", true);
        dao.setDataSource(dataSource);
    }
}
```

- 스프링 컨테이너 없이도 동작하므로 테스트 속도가 가장 빠름
- DI 원칙이 제대로 적용된 코드라면 컨테이너 없이도 테스트 가능

## DI를 이용한 테스트 방법 선택 기준

| 방법 | 장점 | 단점 | 사용 시기 |
|---|---|---|---|
| 컨테이너 없는 DI 테스트 | 빠름, 간결 | 스프링 기능 사용 불가 | 단순 로직 테스트 |
| 테스트 전용 설정 파일 | 컨텍스트 공유 가능 | 설정 파일 추가 관리 | 대부분의 경우 권장 |
| `@DirtiesContext` | 유연한 DI 변경 | 컨텍스트 재생성 비용 | 불가피하게 컨텍스트 변경 시 |

> **우선순위**: 컨테이너 없는 DI 테스트 → 테스트 전용 설정 파일 → `@DirtiesContext`

## 정리

> 스프링 테스트 컨텍스트 프레임워크를 사용하면 ApplicationContext를 여러 테스트가 공유할 수 있어  
> 테스트 실행 속도를 크게 향상시킬 수 있다. 테스트 전용 설정 파일을 분리하는 것이 가장 권장되는 방식이다.
