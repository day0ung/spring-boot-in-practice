# 1.6 싱글톤 레지스트리와 오브젝트 스코프

## 오브젝트의 동일성과 동등성

- `DaoFactory`를 직접 사용할 경우 `userDao()`를 호출할 때마다 **새로운 오브젝트**가 생성됨
- 반면 애플리케이션 컨텍스트에서 `getBean()`을 여러 번 호출해도 **동일한 오브젝트**를 반환

```java
UserDao dao1 = context.getBean("userDao", UserDao.class);
UserDao dao2 = context.getBean("userDao", UserDao.class);

System.out.println(dao1 == dao2); // true (동일한 오브젝트)
```

## 싱글톤 레지스트리로서의 애플리케이션 컨텍스트

- 스프링은 기본적으로 빈 오브젝트를 **싱글톤**으로 만들어 관리
- 서버 환경에서 매 요청마다 새 오브젝트를 생성하면 GC 부담이 매우 커짐
- 따라서 서비스 오브젝트는 싱글톤으로 사용하는 것이 권장됨

## 싱글톤 패턴의 한계

일반적인 싱글톤 패턴은 아래와 같은 문제가 있음

```java
public class UserDao {
    private static UserDao INSTANCE;

    private UserDao(ConnectionMaker connectionMaker) { ... }

    public static synchronized UserDao getInstance() {
        if (INSTANCE == null) INSTANCE = new UserDao(...);
        return INSTANCE;
    }
}
```

| 문제점 | 설명 |
|---|---|
| private 생성자 | 상속 불가, 다형성 적용 불가 |
| 테스트 어려움 | 목(Mock) 오브젝트로 대체하기 어려움 |
| 전역 상태 | 어디서든 접근 가능한 전역 상태를 만들어 객체지향 설계에 반함 |
| 서버 환경 문제 | 클래스 로더 구성에 따라 싱글톤이 보장되지 않을 수 있음 |

## 싱글톤 레지스트리

- 스프링은 직접 싱글톤 패턴을 구현하지 않아도 **싱글톤으로 빈을 관리**해줌
- **싱글톤 레지스트리**: 싱글톤 오브젝트를 생성하고 관리하는 스프링의 기능
- 덕분에 평범한 자바 클래스(public 생성자, 일반 클래스)도 싱글톤으로 활용 가능
- 테스트 환경에서도 자유롭게 오브젝트를 만들고 주입 가능 → **테스트 용이성 확보**

## 싱글톤과 오브젝트의 상태

- 싱글톤 빈은 여러 스레드에서 동시에 사용됨 → **stateless(무상태)** 로 설계해야 함
- 인스턴스 변수에 상태 정보를 저장하면 멀티스레드 환경에서 심각한 문제 발생
- 읽기 전용 정보나 `DataSource` 같은 오브젝트 참조는 인스턴스 변수로 사용 가능

```java
// 위험한 예시 - 인스턴스 변수에 상태 저장
public class UserDao {
    private Connection c;       // ❌ 멀티스레드 환경에서 위험
    private User user;          // ❌ 멀티스레드 환경에서 위험

    private ConnectionMaker connectionMaker; // ✅ 읽기 전용 참조는 괜찮음
}
```

## 스프링 빈의 스코프

- **싱글톤 스코프**: 기본값. 컨테이너당 하나의 오브젝트만 생성
- **프로토타입 스코프**: `getBean()` 호출마다 새로운 오브젝트 생성
- **요청 스코프**: HTTP 요청마다 생성 (웹 환경)
- **세션 스코프**: HTTP 세션마다 생성 (웹 환경)

## 정리

> 스프링의 싱글톤 레지스트리 덕분에, 일반 자바 클래스도 싱글톤 패턴의 단점 없이  
> 싱글톤으로 관리될 수 있다. 단, 싱글톤 빈은 반드시 무상태(stateless)로 설계해야 한다.
