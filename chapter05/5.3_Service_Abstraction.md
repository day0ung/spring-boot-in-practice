# 5.3 서비스 추상화와 단일 책임 원칙

## 수직/수평 계층 구조와 분리

- `UserDao`는 데이터 액세스 로직, `UserService`는 비즈니스 로직 → **수평적 분리**
- `UserService`는 트랜잭션 기술에 독립적 → **수직적 분리** (추상화 계층)

```
[UserService] ─── 비즈니스 로직
     │
[PlatformTransactionManager] ─── 트랜잭션 추상화
     │
[DataSourceTransactionManager / JtaTransactionManager ...]
     │
[UserDao] ─── 데이터 액세스
     │
[JdbcTemplate] ─── JDBC 추상화
     │
[DataSource / DB]
```

## 단일 책임 원칙 (SRP, Single Responsibility Principle)

> "하나의 클래스는 하나의 책임만 가져야 한다"

- 변경 이유가 두 가지 이상인 클래스는 SRP를 위반
- `UserService`가 트랜잭션 코드를 직접 다루면 두 가지 책임을 가짐:
  1. 사용자 레벨 관리 비즈니스 로직
  2. 트랜잭션 관리 기술

- 트랜잭션 서비스 추상화로 `UserService`는 **비즈니스 로직만** 책임지게 됨

### SRP 위반 예시

```java
// 트랜잭션 기술이 바뀌면 UserService도 변경해야 함 → SRP 위반
public void upgradeLevels() throws Exception {
    Connection c = dataSource.getConnection(); // JDBC에 종속
    c.setAutoCommit(false);
    // ...
}
```

### SRP 준수 예시

```java
// 트랜잭션 기술이 바뀌어도 UserService는 변경 불필요
public void upgradeLevels() {
    TransactionStatus status =
        transactionManager.getTransaction(new DefaultTransactionDefinition());
    try { ... }
    // ...
}
```

## 스프링의 의존관계 주입(DI)과 단일 책임 원칙

- DI는 SRP를 지킬 수 있게 도와주는 핵심 도구
- 각 계층이 인터페이스에만 의존하면 구현 기술이 바뀌어도 서로 영향을 주지 않음

| 변경 이유 | 영향 범위 |
|---|---|
| 업그레이드 조건 변경 | `UserService`만 변경 |
| DB 접근 기술 변경 (JDBC → JPA) | `UserDao` 구현체만 변경 |
| 트랜잭션 기술 변경 (JDBC → JTA) | XML 설정만 변경 |

## 정리

> 서비스 추상화는 단순히 코드를 재사용하는 것이 아니라,  
> 각 계층이 자신의 책임에만 집중할 수 있도록 하는 설계 원칙이다.  
> DI는 이를 가능하게 하는 핵심 메커니즘이다.
